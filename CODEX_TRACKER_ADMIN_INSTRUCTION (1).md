# Техническое задание для Codex: два сайта — публичный трекер и отдельная админка

## Как использовать этот документ

Передай этот файл Codex как основное техническое задание. Codex должен сначала изучить существующий проект и текущий код, затем составить короткий план и только после этого вносить изменения.

Если проект уже существует, нельзя удалять или без необходимости переписывать рабочие файлы. Нужно развивать текущий проект, сохраняя существующий дизайн, данные Firebase и работающие функции.

---

## 1. Главная задача

Создать **два самостоятельных сайта** с разными адресами и отдельными сборками:

1. **Сайт №1 — публичный трекер.** Его открывают ученики и посетители. Он только читает и показывает данные.
2. **Сайт №2 — закрытая админка.** Её открывает владелец. Она добавляет, изменяет и удаляет данные, которые сразу отображаются на сайте-трекере.

Это должны быть именно два сайта, а не две страницы `/` и `/admin` внутри одного сайта.

Оба сайта должны подключаться к одному Firebase-проекту и одной базе Cloud Firestore. Благодаря этому изменения из админки автоматически появляются на публичном трекере.

Рекомендуемая организация кода — один общий репозиторий с двумя независимыми приложениями:

```text
tracker-system/
├── tracker-site/        // отдельный публичный сайт
└── admin-site/          // отдельный закрытый сайт
```

У каждого приложения должны быть собственные `package.json`, `src`, `index.html`, `.env.local`, команды запуска и production build. Они могут использовать одинаковый Firebase Web Config, потому что работают с одной базой.

Рекомендуемые адреса после публикации:

```text
https://tracker.example.com        // публичный трекер
https://admin.example.com          // закрытая админка
```

Допустимы и стандартные адреса Firebase Hosting, Vercel или другого выбранного хостинга.

## 2. Контекст существующей базы

Firebase-проект уже создан. Cloud Firestore уже содержит данные первой группы.

Текущая структура:

```text
Gr1                         // коллекция группы
├── Simeon                  // документ ученика
│   ├── hw1: 0
│   ├── hw2: 0
│   ├── hw3: 0
│   ├── hw4: 0
│   └── hw5: 0
└── Sonya                   // документ ученицы
    ├── hw1: 0
    ├── hw2: 0
    ├── hw3: 0
    ├── hw4: 0
    └── hw5: 0
```

На первом этапе нужно работать с существующей коллекцией `Gr1`. Не мигрировать данные и не переименовывать коллекцию без отдельного согласования с владельцем проекта.

Документы должны хранить только имя или безопасный псевдоним ученика и значения трекера. Не добавлять в публичную базу фамилии, телефоны, email, адреса и другие персональные данные детей.

## 5. Публичный сайт-трекер

### Назначение

Публичная страница показывает актуальную таблицу группы `Gr1`. Посетители могут видеть данные, но не могут изменять их.

### Обязательные функции

- Загрузка документов коллекции `Gr1` из Firestore.
- Отображение учеников строками.
- Отображение заданий `hw1`, `hw2`, `hw3`, `hw4`, `hw5` столбцами.
- Понятное визуальное отображение значения каждого задания.
- Автоматическое обновление интерфейса после изменения данных в Firestore. Предпочтительно использовать `onSnapshot`.
- Состояние загрузки.
- Понятное сообщение при ошибке подключения.
- Пустое состояние, если учеников ещё нет.
- Корректная работа на телефоне и компьютере.

### Ограничения

- На публичной странице не должно быть кнопок добавления, редактирования или удаления.
- Нельзя полагаться только на скрытие кнопок: запись должна быть запрещена правилами Firestore.
- Не показывать конфиденциальные данные.
- Не размещать служебные сообщения Firebase и технические ошибки прямо перед пользователем. В консоль можно выводить подробности, а на странице — понятный текст.

## 6. Админ-панель

### Отдельный адрес

Админка должна быть самостоятельным приложением и публиковаться по отдельному адресу. Она не должна быть маршрутом `/admin` публичного трекера.

### Доступ

Админ-панель должна требовать вход через Firebase Authentication. Предпочтительный вариант — Google Sign-In. Если в существующем проекте уже используется Email/Password, сохранить этот способ.

После входа приложение должно проверить пользователя. Изменять данные может только аккаунт, чей Firebase `UID` разрешён правилами Firestore.

Если пользователь не вошёл:

- показать экран входа;
- не загружать инструменты редактирования.

Если вошёл посторонний пользователь:

- показать сообщение «У вас нет доступа к админ-панели»;
- не показывать элементы управления;
- не пытаться обходить правила Firestore.

### Обязательные функции администратора

- Просматривать текущих учеников `Gr1`.
- Добавлять ученика.
- Редактировать отображаемое имя ученика.
- Изменять значения `hw1`–`hw5`.
- Удалять ученика только после подтверждения.
- Выходить из аккаунта.
- Видеть состояние сохранения и результат операции.
- Не отправлять повторную запись при многократном нажатии.

### Работа с документами

Для новых документов предпочтительно использовать автоматически созданный Firestore ID, а имя хранить в поле `name`. Однако существующие документы `Simeon` и `Sonya` уже используют имя как ID, поэтому Codex должен обеспечить обратную совместимость.

Рекомендуемый формат нового документа:

```javascript
{
  name: "Alex",
  hw1: 0,
  hw2: 0,
  hw3: 0,
  hw4: 0,
  hw5: 0,
  createdAt: serverTimestamp(),
  updatedAt: serverTimestamp()
}
```

При чтении существующего документа без поля `name` использовать его `documentId` как отображаемое имя. Не выполнять массовое изменение старых документов автоматически.

### Валидация

- Имя обязательно.
- Убирать пробелы в начале и конце.
- Не создавать пустые имена.
- Не создавать очевидные дубликаты без предупреждения.
- Значения `hw1`–`hw5` должны соответствовать текущей логике трекера.
- Если сейчас используется `0/1`, не расширять систему значений без согласования.

## 8. Firebase Config для двух сайтов

Firebase Web Config нужно подключить к обоим приложениям через переменные окружения. Поскольку сайты работают с одним Firebase-проектом, основные значения конфигурации у них совпадают.

Создать отдельный локальный файл `.env.local` внутри `tracker-site`:

```dotenv
VITE_FIREBASE_API_KEY=значение_из_Firebase
VITE_FIREBASE_AUTH_DOMAIN=значение_из_Firebase
VITE_FIREBASE_PROJECT_ID=значение_из_Firebase
VITE_FIREBASE_STORAGE_BUCKET=значение_из_Firebase
VITE_FIREBASE_MESSAGING_SENDER_ID=значение_из_Firebase
VITE_FIREBASE_APP_ID=значение_из_Firebase
VITE_FIREBASE_GROUP_COLLECTION=Gr1
```

Создать отдельный `.env.local` внутри `admin-site`:

```dotenv
VITE_FIREBASE_API_KEY=значение_из_Firebase
VITE_FIREBASE_AUTH_DOMAIN=значение_из_Firebase
VITE_FIREBASE_PROJECT_ID=значение_из_Firebase
VITE_FIREBASE_STORAGE_BUCKET=значение_из_Firebase
VITE_FIREBASE_MESSAGING_SENDER_ID=значение_из_Firebase
VITE_FIREBASE_APP_ID=значение_из_Firebase
VITE_FIREBASE_ADMIN_UID=UID_владельца
VITE_FIREBASE_GROUP_COLLECTION=Gr1
```

В каждом приложении создать `.env.example` без реальных значений. В публичном трекере строка `VITE_FIREBASE_ADMIN_UID` не нужна.

```dotenv
VITE_FIREBASE_API_KEY=
VITE_FIREBASE_AUTH_DOMAIN=
VITE_FIREBASE_PROJECT_ID=
VITE_FIREBASE_STORAGE_BUCKET=
VITE_FIREBASE_MESSAGING_SENDER_ID=
VITE_FIREBASE_APP_ID=
VITE_FIREBASE_ADMIN_UID=
VITE_FIREBASE_GROUP_COLLECTION=Gr1
```

Убедиться, что оба файла `.env.local` добавлены в `.gitignore`.

Пример инициализации:

```javascript
import { getApps, initializeApp } from 'firebase/app';
import { getAuth } from 'firebase/auth';
import { getFirestore } from 'firebase/firestore';

const firebaseConfig = {
  apiKey: import.meta.env.VITE_FIREBASE_API_KEY,
  authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
  projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
  storageBucket: import.meta.env.VITE_FIREBASE_STORAGE_BUCKET,
  messagingSenderId: import.meta.env.VITE_FIREBASE_MESSAGING_SENDER_ID,
  appId: import.meta.env.VITE_FIREBASE_APP_ID,
};

const app = getApps().length ? getApps()[0] : initializeApp(firebaseConfig);

export const db = getFirestore(app);
```

В `tracker-site` достаточно экспортировать `db`. В `admin-site` дополнительно импортировать `getAuth` и экспортировать `auth`:

```javascript
import { getAuth } from 'firebase/auth';

export const auth = getAuth(app);
```

Важно:

- Не использовать и не добавлять в браузерный проект Firebase Admin SDK.
- Не помещать JSON service account в репозиторий.
- Не коммитить приватные ключи.
- Firebase Web Config не заменяет правила безопасности Firestore.

## 9. Правила Cloud Firestore

Для текущей структуры `Gr1/{studentId}` использовать правила, в которых читать данные могут посетители, а изменять — только владелец.

Перед публикацией заменить `ВСТАВИТЬ_UID_ВЛАДЕЛЬЦА` на реальный UID из Firebase Authentication.

```firebase
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    function isOwner() {
      return request.auth != null
        && request.auth.uid == "ВСТАВИТЬ_UID_ВЛАДЕЛЬЦА";
    }

    match /Gr1/{studentId} {
      allow read: if true;
      allow create, update, delete: if isOwner();
    }
  }
}
```

Правила нужно опубликовать в Firebase Console: **Firestore → Rules → Publish**.

Не использовать в финальной версии:

```firebase
allow read, write: if true;
```

Если появятся `Gr2`, `Gr3` и другие группы, не открывать произвольные коллекции автоматически. Добавить только необходимые разрешённые пути или согласовать новую масштабируемую структуру данных.

## 10. Firebase Authentication

Codex должен реализовать клиентскую часть авторизации, но владелец проекта должен включить выбранный провайдер в Firebase Console:

```text
Authentication → Sign-in method → Google или Email/Password → Enable
```

Для Google Sign-In использовать Firebase Web SDK и корректно обрабатывать:

- успешный вход;
- закрытие окна входа;
- ошибку входа;
- восстановление сессии после перезагрузки;
- выход.

Проверка `VITE_FIREBASE_ADMIN_UID` в интерфейсе нужна для удобства, но настоящая защита записи должна оставаться в Firestore Rules.

Интерфейс должен выглядеть как законченный современный продукт, а не как техническая заготовка.

- удобная таблица на компьютере;

Не использовать случайные эмодзи вместо единой системы иконок. Не перегружать страницу декором и анимациями.

## 13. Развёртывание двух сайтов

Публичный трекер и админку нужно собирать и публиковать независимо. У каждого сайта должен быть собственный URL.

Предпочтительный вариант при использовании Firebase — Firebase Hosting multisite внутри уже существующего Firebase-проекта:

```text
tracker-site  → отдельный Hosting site для публичного трекера
admin-site    → отдельный Hosting site для админки
```

Также допустимы два отдельных проекта Vercel или другой выбранный владельцем хостинг. При этом Firebase-проект и Firestore остаются общими.

Для каждого сайта отдельно:

1. Добавить его переменные `VITE_FIREBASE_*` в настройки хостинга.
2. Выполнить production build из соответствующей папки.
3. Опубликовать именно папку `dist` этого приложения.
4. Проверить его URL после публикации.

Оба домена нужно добавить в Firebase Console в список разрешённых доменов Authentication. Особенно это важно для отдельного домена админки.

Нельзя публиковать две сборки в одну и ту же папку Hosting: последняя публикация перезапишет предыдущий сайт.

## 14. Порядок реализации

1. Изучить существующий проект и Firebase-подключение.
2. Исправить или создать модуль Firebase initialization внутри каждого приложения.

9. Добавить загрузку, ошибки, пустые состояния и подтверждения.
10. Проверить адаптивность обоих сайтов.

12. Подготовить две независимые конфигурации публикации.
13. Просмотреть итоговые изменения и убедиться, что не затронуты посторонние файлы.

## 15. Проверка результата

Codex должен проверить как минимум следующие сценарии:

### Публичный пользователь

- Открывает `/` без авторизации.
- Видит `Simeon`, `Sonya` и значения `hw1`–`hw5`.
- Не видит кнопок редактирования.
- Не может изменить данные через приложение.

### Владелец

- Открывает отдельный URL сайта-админки.
- Входит через настроенный Firebase Authentication.
- Видит список учеников.
- Может добавить ученика.
- Может изменить значение задания.
- Может переименовать ученика без потери остальных значений.
- Может удалить ученика после подтверждения.
- После обновления страницы данные остаются в Firestore.
- После выхода теряет доступ к управлению.

### Посторонний авторизованный пользователь

- Не получает доступ к инструментам управления.
- Запрос записи отклоняется Firestore Rules.

### Техническая проверка

- `npm run build` завершается успешно.
- `npm run lint` завершается успешно, если lint настроен.
- В консоли браузера нет необработанных ошибок.
- Публичный сайт и админка открываются по двум разным URL.
- Изменение в админке появляется на публичном сайте.
- Production build успешно выполняется отдельно для каждого приложения.
- В репозитории нет service account, приватных ключей и заполненного `.env.local`.

## 16. Критерии готовности

Задача считается выполненной, когда:

- публичный трекер читает реальные данные из коллекции `Gr1`;
- трекер и админка являются двумя отдельными сайтами с разными URL;
- оба сайта используют один Firebase-проект и одну коллекцию `Gr1`;
- изменение, сделанное в админке, отображается в публичном трекере;
- только разрешённый Firebase UID может изменять данные;
- существующие документы `Simeon` и `Sonya` продолжают работать;
- данные сохраняются после обновления страницы;
- интерфейс адаптирован для телефона и компьютера;
- production build проходит без ошибок;
- правила Firestore и ручные действия в Firebase описаны владельцу;
- Codex предоставляет краткий итог: какие файлы изменены, что проверено и что владельцу осталось сделать вручную.

## 17. Что Codex не должен делать

- Не создавать второй Firebase-проект.
- Не объединять трекер и админку в один сайт с маршрутом `/admin`.
- Не размещать обе production-сборки по одному адресу.
- Не создавать второй репозиторий без необходимости: достаточно одного репозитория с двумя приложениями.
- Не удалять текущую коллекцию `Gr1`.
- Не переименовывать `Simeon` и `Sonya` автоматически.
- Не включать публичную запись в Firestore.
- Не использовать Firebase Admin SDK в браузере.
- Не добавлять service account или секретные ключи в проект.
- Не оставлять `allow read, write: if true`.
- Не менять хостинг, стек или дизайн радикально без согласования.
- Не объявлять задачу завершённой, пока не выполнены сборка и базовая проверка сценариев.

## 18. Формат итогового ответа Codex

После выполнения Codex должен написать простым языком:

1. Что создано.
2. Какие файлы изменены.
3. Какие проверки выполнены.
4. Какие действия нужно сделать вручную в Firebase Console.
5. Где вставить Firebase Config и UID.
6. Как запустить проект локально.
7. Как открыть публичный трекер и отдельный сайт-админку.
8. Какие два URL получились после публикации.
